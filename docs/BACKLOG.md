## Bugs

- [ ] **BUG-02** (P1) Deduplication executor silently no-ops when `replacements` keys don't match resolved plan paths — `_update_single_file` (`src/ast_grep_mcp/features/deduplication/applicator_executor.py:147`) looks up `replacements.get(file_path, {})` by the exact orchestration-plan path. `applicator._resolve_file_paths` (`applicator.py:397-404`) converts plan paths to **absolute** paths, while the pre-validator (`applicator_validator.py:86-90`, `_resolve_file_path`) explicitly accepts **relative** replacement keys by joining with `project_folder` — signaling relative keys are a supported input shape. When `generated_code.replacements` uses relative keys (e.g. `"src/foo.py"`), pre-validation passes, the executor's lookup with `/abs/project/src/foo.py` misses, and the file is read and rewritten **unchanged** (mtime touched, import possibly injected) — then reported in `files_modified` with `status: "success"`. The duplicate code is never actually replaced.
  - **Repro:** build an orchestration plan whose `update_files[].path` entries are project-relative, with `replacements` keyed the same way; run apply. Result: success response, zero content changes.
  - **Fix direction:** normalize both plan paths and replacement keys to absolute (or canonical relative) form in one place before execution — e.g. resolve replacement keys in `_resolve_file_paths` alongside `files_affected` — and/or treat a missing replacement entry for a planned update file as an error rather than an empty dict.
  - **Debugging context:** lookup miss returns `{}` so `replacement.get("new_content")` is falsy and the original content is written back at `applicator_executor.py:153-154`; related silent-skip at `applicator_executor.py:127-128` where planned files missing on disk are dropped without a `failed_files` entry. Verified 2026-07-21 (dedup module review).

- [ ] **BUG-06** (P2) Per-candidate enrichment timeout is dead code; a hung enrichment blocks the tool forever — `analysis_orchestrator.py:481-484` calls `as_completed(futures)` **without** a timeout, then `future.result(timeout=timeout_seconds)` on futures that are already complete, which can never raise `TimeoutError`. The whole timeout apparatus (`_resolve_timeout`, the `TimeoutError` branch at `:401-407`, `DEFAULT_TIMEOUT_PER_CANDIDATE_SECONDS`) is unreachable; one hung coverage lookup blocks the MCP call indefinitely. Fix: `as_completed(futures, timeout=...)` or `concurrent.futures.wait` with deadlines. (2026-07-21 dedup module review)
- [ ] **BUG-07** (P2) Exclude patterns applied after the stream limit truncates results — `detector.py:257-270` collects up to `max_constructs` (default 1000) matches from `stream_ast_grep_results` **before** `_apply_exclude_patterns` filters paths. If `.venv`/`node_modules` matches appear early in the walk they consume the entire budget and are then discarded, so real project code is never analyzed; the `construct_limit_reached` log compares the post-filter count, hiding the truncation. Fix: filter inside the stream loop (or pass excludes to ast-grep) so the limit applies to kept matches. (2026-07-21 dedup module review)

Fix: include `target_file` in the backup set and track created files for deletion on rollback. (2026-07-21 dedup module review)

- [ ] **BUG-12** (P2) Similarity/embedding/score caches keyed by `hash()` with no collision check and no size bound — `similarity.py:219-221` (MinHash signatures), `similarity.py:1241-1248` (CodeBERT 768-float embeddings), `ranker.py:398` (`f"cache_{abs(hash(...))}"`).
